```text
│ explicit decision           │ → decision/state
│ actionable request          │ → task candidate
│ architecture change         │ → decision + task
└─────────────────────────────┘
```

And provenance remains attached so another agent knows **you decided something**, versus ChatGPT merely suggesting it.

### The technical catch with normal ChatGPT mobile

This is the part we shouldn't pretend is solved by Markdown.

`CHATGPT.md` can establish expected behavior for an environment that actually loads it, but a completely ordinary new ChatGPT mobile conversation isn't automatically running your repository's `before_work()` and `after_work()` scripts.

We therefore need to determine **what integration point ChatGPT actually gives Outer Heaven** and design around that—connected sources/actions, an external continuity service, API integration, or another supported mechanism—rather than designing a hook ChatGPT mobile cannot execute.

The same audit needs to happen separately for:

**ChatGPT mobile/web/desktop, Cursor, Claude/Claude Code, Codex, and Grok Bot.**

Some may support near-perfect automatic hooks. Others may need the continuity service to do more of the work.

So I would add another hard requirement to the master implementation directive:

> **Do not claim a platform has automatic read/write continuity merely because its adapter instructs it to. Demonstrate the integration on each supported surface. A surface receives `AUTO-READ PASS` and `AUTO-APPEND PASS` only after an end-to-end test proves that a normal user session can trigger the behavior without the owner manually requesting synchronization.**

That's the standard I'd use.

Your desired experience is absolutely:

**open normal app → start talking → Outer Heaven is already there → meaningful conversation automatically feeds Outer Heaven back.**

But we need to make the infrastructure earn that behavior on each platform rather than relying on the AI to remember to do it.
