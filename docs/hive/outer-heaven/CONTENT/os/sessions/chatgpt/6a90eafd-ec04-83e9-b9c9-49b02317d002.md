## Core principle

Do not reproduce manually what an available specialized tool can perform better.

Before performing a non-trivial task, determine:

1. What outcome is required?
2. What capabilities are required?
3. Which available system provides each capability best?
4. Is that capability actually callable from this environment?
5. What is the lowest-friction invocation method?
6. Should one system perform the whole task or should several systems collaborate?

Then execute the best route automatically when authorized.

For every supported platform, discover and maintain:

- feature name

- suitable task types
- invocation method
- CLI command if available
- API endpoint/tool if available
- MCP tool if available
- plugin if available
- local application integration
- required credentials
- required permissions
- input requirements
- expected output
- strengths
- weaknesses
- cost
- latency
- context limits
- whether it supports parallel execution
- whether it changes files
- whether it accesses the browser

Periodically inspect official documentation, installed CLI help, plugin manifests, MCP tool schemas, configuration files, and release notes to discover new or changed capabilities.

# CALLABILITY TEST

A feature existing in a product does NOT mean you can invoke it.

Classify every capability as:

AVAILABLE_DIRECTLY
AVAILABLE_VIA_CLI
AVAILABLE_VIA_API
AVAILABLE_VIA_MCP
AVAILABLE_VIA_PLUGIN
AVAILABLE_VIA_BROWSER
AVAILABLE_VIA_COMPUTER_CONTROL
AVAILABLE_VIA_OTHER_AGENT
UNAVAILABLE

Never claim that another AI system was invoked unless you actually invoked it.

If a feature is useful but not callable, determine whether an MCP server, CLI, API, plugin, or bridge can expose it.

# EXECUTION POLICY

Think in terms of:

OUTCOME → REQUIRED CAPABILITIES → BEST TOOLS → EXECUTION GRAPH

rather than:

PROMPT → ONE MODEL → ANSWER

The objective is not to maximize usage of Claude, Codex, Cursor, or Grok.

The objective is to achieve the user's requested outcome using the strongest combination of available capabilities with minimal unnecessary effort, cost, duplication, and human intervention.

If several tools are equivalent, prefer:

1. directly callable
2. reliable
3. already authenticated
4. repository/context aware
5. lower friction
6. lower cost
7. faster

unless task quality justifies another choice.

Always verify the final outcome rather than assuming that a successful tool invocation means the task succeeded.
:::

OpenAI's current plugin system specifically separates **apps** that connect to external services from **plugins** that package workflows using apps and/or skills, so those need to be inventoried separately rather than all being called “tools.” citeturn596939search3turn596939search4

### Don't merge provider-specific behavior blindly

You may have a Claude skill that depends on Claude-specific behavior.

Keep:

```text
canonical workflow
```

separate from:

```text
Claude implementation
Codex implementation
Cursor implementation
```

For example:

```text
.agents/skills/
└── production-audit/
    ├── SKILL.md
    ├── providers/
    │   ├── claude.md
    │   ├── codex.md
    │   └── cursor.md
    └── scripts/
```

`SKILL.md` describes **what the procedure means**.

Provider files explain **how that platform should execute it**.

That's much safer.

### You should also preserve provenance

Every extracted fact should know where it came from.

For example:

```yaml
fact:
  "Forge uses Supabase Auth"

sources:
  - claude_project: Forge
    conversation: ...
  - github_repo: forge
    file: src/auth/client.ts

confidence: high
last_verified: 2026-08-25
```

Why?

Because six months later an agent may discover the repo has moved away from Supabase.

Then Outer Heaven can mark the old information:

```text
SUPERSEDED
```

instead of continuing to teach every agent stale architecture.
