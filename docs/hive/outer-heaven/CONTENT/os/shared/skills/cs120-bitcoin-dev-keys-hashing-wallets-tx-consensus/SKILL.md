# Bitcoin for developers: keys, hashing, wallets, tx, consensus (clustered)

**Use when:** a prompt needs **Bitcoin for Developers I** — keys; encodings; signatures and tx validity; hashing/PoW; nodes and wallets; how the open system holds together — in the Saylor CS120 school (18 h). Technical + some coding. **Never send.**

**Do not use when:** reconstructing exams; **PRDV151** (Everybody, not Developers); sending/broadcasting a transaction; wallet-seed paste; investment or trading advice; inventing SHA-256 / ECDSA / secp256k1 / Base58 as Saylor-titled; promising ACE; sitting the final.

This is **one** skill. Eight live units, **six** live CLOs. Loop: **keys then encodings then signatures/tx-validity then unnamed algorithms then nodes/wallets then system-summary (PoW overlay).** Do not mint eight unit-skills.

## 1. Procedure — six checks

Run in order. Stop if Check A says another school, send, or trade.

### Check A — Identity overlay (always)

| Prompt smells like | Hand off |
|---|---|
| "Bitcoin for non-developers / everybody" | **PRDV151** (different course — do not merge) |
| "Should I buy / send this coin" | **Personal CFO / Wealth Manager** after literacy; **HITL — refuse send** |

| "How keys, hashes, nodes, wallets fit" | **this skill** |
| "Sit the CS120 final" | **refuse** — no exams this cycle |

**Primary goal:** developer literacy for Bitcoin's components. Named failure mode: sending a tx, merging with PRDV151, or minting algorithm names as Saylor titles.

### Check B — Keys and encryption (when "public/private / symmetric" is in play)

CLO 1, CLO 4 overlay. Units 2–3.

**Symmetric vs asymmetric encryption; public vs private keys. Differentiate encryption algorithms used in Bitcoin and list their contribution** — **algorithm names are not live.** Do not mint SHA-256 / ECDSA / secp256k1 as Saylor-titled. If the prompt already uses those words, treat as this CLO without claiming the syllabus named them.

Shape: name the key type, then the job (encrypt vs sign). Intro: keys used in Bitcoin transactions.

### Check C — Encodings (when "hex / base58-ish / convert this payload" is in play)

CLO 2. Unit 5 overlay (Bitcoin Data).

**Convert data between encoding methods used in Bitcoin.** Method names are **not** listed. Do not mint Base58 / Bech32 / hex as Saylor titles.

Shape: convert as a job. Don't invent the named encodings.

### Check D — Transaction validity and signatures (when "is this tx valid / signature check" is in play)

CLO 3. Units 3 and 7. Unit 7 title **Transactions and Scripting** — scripting is overlay, not a CLO word. Do not mint Script / opcodes as Saylor-titled.

**Determine validity of a Bitcoin transaction by evaluating the transaction data and signature.**

Shape: data + signature → valid or not. **Literacy. Do not construct or broadcast a live transaction.**

### Check E — Nodes and wallets (when "what does a wallet do / run a node" is in play)

CLO 5. Unit 6. Intro: list wallet functions; describe node utility.

**Identify components such as nodes and wallets and list their functions.**

Shape: name the component, then its function. Not a custody product. Not a send. Do not paste seeds.

### Check F — System / consensus (when "how does the whole thing hold / PoW" is in play)

CLO 6. Unit 8 Reaching Consensus. Intro: hashing in Bitcoin's **Proof-of-Work** consensus protocol.

**Summarize how the components work together to keep Bitcoin's open, decentralized system running.** PoW is live in intro, not as a CLO word.

Shape: parts → whole. PoW overlay allowed because intro named it. Do not invent longest-chain / difficulty as Saylor titles.
