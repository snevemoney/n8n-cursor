## B. Atomic Knowledge

### Four failure modes; expertise vs just-in-time
- **Claim:** Wrong answers from context are poisoning, bloat, confusion, or clash — not “the model lied for fun.” Expertise (policies, who you are) stays loaded; situational (yesterday’s ticket) is looked up when needed. Dumping tickets into always-on context creates bloat/clash.
- **Reasoning:** Agent will confidently use whatever is in the pile. March vs June refund is a clash, not a personality.
- **Mechanism:** Verify/cross-check/HITL for poison; segment + just-in-time for bloat; fill missing on purpose or refuse; date-stamp policies so clash resolves to newest.
- **Evidence:** refund March/June; principal vs teacher seating chart.
- **Conditions:** You have a place that is supposed to be true.
- **Exceptions:** Poison is “easiest” only if you have a live check.
- **Action:** Do not put every ticket in the always-on brain. HITL on customer email (he names that failure).

## D. Procedures
1. Write a short router: if you need X, look here.
2. Separate always-on expertise from lookup situational.
3. Date-stamp policies so clash has a winner.
4. Read-only audit; you pick fixes.
5. Cron only what must be fresh every week.
6. Split a wiki when it is a distinct growing node.
7. On a miss: reconstruct the search path, then patch routing.
8. Finder-test yourself monthly.

Questions: Is this expertise or situational? Which date wins? Can I walk to this file? Did the index match disk?

Signals: confident June answer in July; “I don’t have access” when you know it is there.
